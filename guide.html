Homelab Guide

A fully declarative single-node homelab. Terraform provisions the VMs & LXCs through the Proxmox API, Talos Linux bootstraps Kubernetes, and Argo CD runs everything in this repo as GitOps — one control plane, one worker, zero manual clicking.

node pve Talos v1.13.4 Kubernetes v1.34 provider bpg/proxmox GitOps Argo CD storage Longhorn · MinIO

Network & VLANs

Four VLANs on the MikroTik (CRS309 gateway + CRS310 switch), trunked to the Proxmox uplink on a VLAN-aware vmbr0. VLAN 20 is the native PVID — guests on VLAN 20 are untagged. VLAN 25 has no internet access by design.

10Trusted10.10.10.0/24taggedyes
20Management10.10.20.0/24native PVID (untagged)yes
24DMZ10.10.24.0/24taggedyes
25Cluster10.10.25.0/24taggedno
VLAN 25 nodes never touch the internet. They pull container images through the Zot mirror at 10.10.20.101:5000 on VLAN 20. Talos has no SSH and no package manager — minimal attack surface.

Firewall automation

ansible/mikrotik.yml configures both MikroTik devices: CRS309 (10.10.1.2) is the L3 gateway + WireGuard + NAT; CRS310 (10.10.1.3) is the PoE managed switch. Run task firewall to apply (requires MIKROTIK_AUTOMATION_PASSWORD and MIKROTIK_DASHBOARD_PASSWORD env vars). VLAN networks are created on the MikroTik; Ansible manages firewall policies and managed users only.

The 6×18 TB Seagate Exos drives (ST18000NM000J-2TV103) are passed raw to the worker VM and used exclusively by MinIO — they do not belong to any Proxmox pool. MinIO runs in distributed mode (EC:2 = 4 data + 2 parity ≈ 72 TB usable). Drives appear as /dev/sdc–/dev/sdh inside the VM.

Kubernetes storage classes

💾

Longhorn

Default class, LUKS-encrypted. Block storage (1 replica) on the beta SSD. 6-hourly backups to MinIO. Every PVC backup is ciphertext before it reaches MinIO.

🪣

MinIO S3

6×18 TB distributed, EC:2. Primary storage for OwnCloud, Immich, Jellyfin (large media). Also receives Longhorn backups. Offsite-encrypted before leaving the house.

📁

local-path

Non-default. Small cache/config volumes (Jellyfin config, Immich model-cache) that don't need replication. Fast, no overhead.

Bootstrap Flow

One command from your PC: cd infrastructure && task all. It runs these phases in order — or run any target on its own.

1
Firewall task firewall

Ansible configures MikroTik firewall policies so the VLANs can talk as needed.

2
Infrastructure task infra

Terraform creates the LXCs and Talos VMs and autostarts them in boot order (registry first).

3
Cluster task cluster

Terraform applies Talos machine configs, bootstraps etcd, and writes kubeconfig + talosconfig.

4
GitOps task gitops

Installs Argo CD and applies the root app-of-apps. Argo then deploys Longhorn, MinIO and your pods automatically.

5
Secrets task secrets:apply

Applies the git-ignored Kubernetes secrets (MinIO root, Longhorn backup creds, PostgreSQL).

Getting Started

Everything you personally must create or fill in before cd infrastructure && task all will work end-to-end. Run it all from your PC.

1 · Things you create outside the repo

🔑

Proxmox API token

In Proxmox: Datacenter → Permissions → API Tokens. Create a token (e.g. root@pam!homelab), give it privileges on /. Paste the USER@REALM!ID=UUID into pve_api_token in proxmox tfvars.

🌐

MikroTik admin password

The existing MikroTik admin password goes in ansible/group_vars/all.sops.yaml as mikrotik_password. Two additional managed users are created automatically by task firewall: the automation user (Ansible) and network-dashboard user (UI). Pass their passwords as env vars: MIKROTIK_AUTOMATION_PASSWORD and MIKROTIK_DASHBOARD_PASSWORD.

🧱

Proxmox host prep

Make vmbr0 VLAN-aware. Trunk VLANs 10/20/24/25 on the MikroTik uplink port (VLAN 20 as native PVID). Attach the 6×18 TB drives — run the qm set commands from terraform.tfvars.example after task infra creates the worker VM. Have the LXC template (debian-13-standard) and beta SSD pool present.

🔐

SSH key

Your public key goes in ssh_public_keys in proxmox tfvars — injected into LXCs and the gameserver VM. Talos nodes have no SSH.

🔒

Age keypair (SOPS)

Run task secrets:init once. This generates your age encryption keypair in _local/age.key (git-ignored). The public key goes in .sops.yaml — it's already set if you cloned this repo. The private key stays only on your machine.

🧰

Tools on your PC

Run task setup (installs via mise): terraform, talosctl, kubectl, sops, age, ansible. Also: ansible-galaxy collection install -r ansible/requirements.yml.

3 · Bring-up order

export MIKROTIK_AUTOMATION_PASSWORD="…" MIKROTIK_DASHBOARD_PASSWORD="…"
task all — runs: firewall → infra → cluster → gitops → secrets:apply

After task infra creates the worker VM, run the qm set commands (in terraform/proxmox/terraform.tfvars.example) to attach the 6×18 TB drives before task cluster.

Almost everything is data in *.tfvars / YAML. Common changes:

Different network layout / VLANs

Edit the vlans map (id → gateway) in terraform/proxmox/variables.tf and the matching vlan_tag / vlan_id locals in images.tf. Move a guest to another VLAN by changing its vlan_key + IP in the tfvars. Set enable_vlan_tagging = false to deploy everything untagged during a transition. Update the firewall rules in ansible/vars/firewall-rules.yml to match.

Resize / re-spec a node

Change cores / memory / disk_gb for any entry in controlplanes, workers, lxcs or gameservers and re-apply. Disks grow on apply (shrinking isn't supported). Worker data disks live in worker_data_disks (e.g. the 400 GB Longhorn disk).

Add or rename nodes / guests

Guests are for_each maps keyed by the <vlan><ip> name. Add an entry to grow the fleet (e.g. a second worker, another LXC). Keep the controlplane_nodes / worker_nodes maps in the talos module in sync with the names/IPs in the proxmox module.

Change storage pools

Set vm_storage / ct_storage / image_storage in the tfvars, and the storage field of each worker_data_disks entry. When the 6×18 TB gamma drives arrive, attach them to the worker and point MinIO at them — pods only see the S3 endpoint, so no app changes.

Add another gameserver, or skip it

Add entries to the gameservers map (each becomes a Debian + Docker + Wings VM). Set it to {} to provision none. Pelican Panel in kubernetes/apps/pelican-panel manages whatever Wings hosts you register.

4 · Good to know

What runs the cluster?

Talos Linux (immutable, API-managed — no SSH, no apt) running upstream Kubernetes. Operate nodes with talosctl and workloads with kubectl; node changes are machine-config patches in the talos Terraform module.

How do I add a new service / pod?

Create kubernetes/apps/<name>/ with your manifests, commit, and Argo CD deploys it (the app-of-apps recurses and ignores *.example.yaml). Use Longhorn for volumes and the in-cluster PostgreSQL / MinIO for data. See docs/roadmap.md.

Where do secrets live?

All secrets are age-encrypted SOPS files (*.sops.yaml) committed to Git. Argo CD deliberately excludes them — it only applies plaintext manifests. task secrets:apply decrypts and applies them to the live cluster. To edit any secret: task secrets:edit -- path/to/file.sops.yaml. Talos PKI lives in the talos Terraform state file — keep that file off Git and treat it as sensitive. The age private key lives in _local/age.key (git-ignored) — back it up to Vaultwarden.

What does task secrets:init do?

It generates an age keypair at _local/age.key. This is a one-time setup step per workstation. It does NOT create or fill any passwords — those go in the *.sops.yaml files. The public key is already in .sops.yaml; SOPS uses it to encrypt. The private key is used at runtime (via SOPS_AGE_KEY_FILE) to decrypt. Think of it as: init = create your lock and key, filling secrets = putting valuables in the safe.

Disaster Recovery

The "house burned down" playbook: what's backed up where, how it stays private, and how to rebuild on a new (identically specced) server.

Two backup paths

Two kinds of data, each encrypted before it leaves the house:

  1. Pod volumes (Longhorn) — PostgreSQL, Pelican, etc. on the beta SSD use the LUKS-encrypted default StorageClass longhorn-encrypted (key: longhorn-crypto). A RecurringJob backs them up every 6 h (keep 8) to local MinIO bucket longhorn-backups, and an mc mirror CronJob ships that bucket to your friend's MinIO every 3 h. Encryption sits below the backup, so it's ciphertext throughout.
  2. MinIO app data — ownCloud, immich, etc. write straight into MinIO and are not encrypted at rest. A separate CronJob uses rclone crypt (key: offsite-crypt) to encrypt contents and object names client-side, then sync every bucket to your friend every 6 h. Jellyfin is excluded (re-acquirable media), as is the already-encrypted longhorn-backups — both configurable via EXCLUDE_BUCKETS.
Why your friend can't read either: privacy comes from your two passphrases (longhorn-crypto, offsite-crypt), not his MinIO permissions. He hosts opaque, scrambled-name blobs only.

Rebuild on a new server

  1. Install Proxmox VE; node pve; recreate pools (beta 1TB SSD, ISO/template dir on local); make vmbr0 VLAN-aware. Reattach the 6×18 TB drives (no data loss — they carry their XFS filesystems).
  2. Clone this repo; run task secrets:init (restore _local/age.key from Vaultwarden); restore all *.sops.yaml secrets and every terraform.tfvars.
  3. Run qm set commands to attach the 18 TB drives to the worker VM (see proxmox terraform.tfvars.example).
  4. export MIKROTIK_AUTOMATION_PASSWORD=… MIKROTIK_DASHBOARD_PASSWORD=… then task all. Talos brings the cluster up; Argo CD redeploys everything.
  5. Point Longhorn's backup target at the friend's MinIO (or mc mirror his bucket back into the fresh local MinIO).
  6. Longhorn UI → Backup → restore each volume into its original PVC name. Argo reconciles the apps onto the restored data.
Reachable without a home server? Yes — the off-site copy lives at your friend's independently. You only need his endpoint + creds and your passphrase, from anywhere. Nothing to do at his place beyond him keeping MinIO online.

Test it regularly

Monthly — cheap restore drill

Restore the latest PostgreSQL backup to a new volume, mount it in a throwaway pod, confirm the data reads back, then delete it. Proves passphrase + off-site copy work.

Anytime — off-site readability

From your PC with only the escrowed creds: mc ls offsite/<bucket>. Confirms the remote copy is current and independent of the cluster.

1–2×/year — full rebuild

Run the rebuild steps against a spare/nested Proxmox to confirm a from-zero recovery still works end-to-end, and to learn your real recovery time.

A restore that fails to decrypt almost always means the longhorn-crypto passphrase doesn't match the one used at backup time. Never rotate it while old backups still exist.

Updates

No manual version-chasing. Renovate watches every dependency and opens pull requests; safe ones merge themselves, risky ones wait for a one-click approval.

How it works

🤖

Renovate bot

Config in renovate.json. Tracks Helm charts (Longhorn), container images (PostgreSQL, Pelican, MinIO…), Terraform providers, GitHub Actions, plus the Talos & Kubernetes versions.

✅

Auto-merge (safe)

Patch / minor / digest bumps merge automatically once green. After merge, Argo CD syncs the cluster — truly hands-off.

🙋

Ask-first (risky)

Major upgrades and Talos/Kubernetes bumps are held on the Dependency Dashboard issue — a shorthand list of what changed. Tick a box to approve.

☸️

Cluster upgrades

Talos/k8s version PRs are labelled manual-apply: after merging, run task cluster / talosctl upgrade — they don't apply by a git merge alone.

One-time setup

Enable Renovate on your repo

Install the Renovate GitHub App (or Mend) on your private repo, or run the renovatebot/renovate container on a schedule. It reads renovate.json, opens the Dependency Dashboard issue, and starts proposing updates. For auto-merge, allow it in your branch protection (a solo repo needs no required reviews).

Future: AI-summarised approvals

The ask-first flow already gives a shorthand changelog. A later add-on can layer an LLM that comments a plain-language "what changed / how risky" summary on each held PR — a thin action on top of Renovate, not a rebuild. Not wired up yet.
